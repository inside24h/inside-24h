## 3. "Personalize" for returning users with an old profile: not shown

`AppV4.tsx`. A new key, `i24-start-v2`, marks browsers that have already run the new calm flow. On first load, a profile (`i24-profile`) saved without that key comes from the old "Tell us about you" step. That counts as already answered, so `i24-personalized` is set and the prompt does not appear. A profile saved by the new flow itself (it saves the typical body on the first visit) does not count.

Browser check: a legacy profile gives no prompt after 12 s (`personalized = 1`). A new visitor still gets the prompt, and still gets it on a second visit until they act on it.

Edge case: someone who used the new flow between 2026-10-19 and this change has a profile but no `i24-start-v2`, so they are treated as legacy and won't see the prompt. That is acceptable, because they have already seen the new flow and could personalize from "Your body".

## 5. Performance

Method: Playwright Chromium, mobile 390×844, a transient gzip server, median of 3. Slow 4G = 1.6 Mbps / 150 ms RTT + 4× CPU. "UI" means the React app is mounted (`#root .v4`). Every build was measured the same evening on the same machine.

| Build | entry JS gzip | entry JS min | UI, Slow 4G, `/` | UI, Slow 4G, `#q=cola` | body visible (`#q=cola`) |
|---|---|---|---|---|---|
| d3c3310 (the "1.8 s" commit, rebuilt now) | 169 KB | 504 KB | **1.77 s** | 3.80 s | 5.7 s |
| now, HEAD config (JSON as object literals) | 221 KB | 702 KB | 2.19 s | 4.65 s | 6.0 s |
| now, `json.stringify` + `pureJson()` | 222 KB | 725 KB | 2.18 s | 4.68 s | 5.9 s |
| final `site/` (after the science agent's latest edits) | 228 KB | 741 KB | 2.21 s | 4.85 s | 6.1 s |

The first run's 1.8 s is reproduced exactly, so the numbers are comparable.

Where the +0.4 s comes from: the entry chunk grew by +51 KB gzip. Of that, the food database is +25 KB (14 → 39 KB gzip, from variants, builders and sources). The rest is code: AppV4, share, foodProduct, foodSim, Answers. On Slow 4G (200 KB/s) that is about 0.25 s of download plus parse/eval at 4× CPU.

The food JSON is on the critical path: `parse.ts` imports it synchronously, and the first screen's search, the choosers and deep links need it at once.

What was done:
- `vite.site.config.ts`: `json: { stringify: true }` makes JSON modules `JSON.parse("…")` instead of object literals. `pureJson()` keeps them tree-shakeable; without it `organ-points.json` moved into the first download, and the final build confirms it stays in the lazy `scene3d` chunk.
- Gain: cold evaluation of fooddb goes from about 5 ms to 1.2 ms (Node; about 15 ms saved at 4× CPU). Cost: +1 KB gzip (+23 KB minified, because a string can't be minified). On the network this is neutral (within ±10 ms). It is kept for the main-thread win on slow phones, and the single-file build (vite.v4.config.ts) is unchanged.
- Tried and reverted: `fetchPriority='low'` on the deep-link 3D preloads, so the UI would get bandwidth first. No measurable change (4.87 vs 4.96 s), so it was taken out again and behavior stays the same.

What was not done, and why:
- Lazy-loading the variant / builder / chooser / size data. It is 25 KB of the 39 KB gzip and would save at most ~0.13 s (6%) of the 2.2 s. But `FOODS`, `FOOD_BY_ID`, search (`altList`), choosers and deep-link resolution (`foodFromKey`) all read it synchronously. Making them async changes behavior: typing "kebab" or opening `#q=kebab_wrap…` in the first few hundred ms would give a different result or need a wait state. `foodProduct.ts`, which builds the source claims from it, belongs to the science agent. Not worth the risk for ~0.13 s.
- Trimming fields. The only fields the app never reads are a preset's `check` and an option's `rng`, both used by tests, together 0.4 KB gzip. Sources (`src`: text / cite / url) are 14 KB gzip but the Sources sheet shows them.
- The real next win is the code itself (+26 KB gzip since d3c3310), e.g. splitting the Full / Detailed view and share/export code out of the entry. That belongs in a separate pass.

Single file (`vite.v4.config.ts`): `dist-v4/index-v4.html` is 2.81 MB (gzip 1.135 MB), against 2.57 MB / 1.07 MB on 2026-10-16. Split site: index.html + 19 assets, 2.63 MB uncompressed.
